# Bronze SCD2 history tests

## Architecture

The CRM source only ever gives us **current state** — each batch overwrites
`landing_crm.postcodebase` / `landing_crm.accountbase` with whatever the
source looks like right now, no history included. Full history is built by
**dbt snapshots** (`snapshots/log_postcodebase_snapshot.sql`,
`snapshots/accountbase_snapshot.sql`), which diff each batch's current state
against what was last captured and construct `bronze_crm.log_postcodebase_snapshot`
/ `bronze_crm.accountbase_snapshot` as proper SCD2 tables — `dbt_valid_from`,
`dbt_valid_to` (`NULL` while a row is current), and `dbt_scd_id` are all
generated by dbt itself, not hand-maintained.

That replaces what was originally a hand-rolled mechanism: manually stamped
`valid_from`/`valid_to`/`is_current` columns plus a watermark filter deciding
which rows survived into bronze. That watermark used strict `>` instead of
`>=`, which silently dropped a row (`Cape Town`) whose `updated_ingestion`
matched the watermark exactly — a gap in history that surfaced as a `NULL`
postcode downstream in a point-in-time spine. dbt snapshot's own change
-detection doesn't have that boundary condition to get wrong, which is the
main reason for moving to it rather than just patching the watermark.

These three generic dbt tests exist to catch that whole class of gap — now
pointed at the snapshot's own `dbt_valid_from`/`dbt_valid_to` columns instead
of hand-built ones.

## `no_scd_gaps`

Catches a row missing from the *middle* of an entity's history. For every
row, it looks at the next row (ordered by `valid_from`) and asserts the
current row's `valid_to` equals the next row's `valid_from`. If a version was
dropped, the timeline has a hole and the two surrounding rows won't line up.

`macros/test_no_scd_gaps.sql`
```sql
{% test no_scd_gaps(model, valid_from, valid_to, partition_by=none) %}

with ordered as (

    select
        {{ valid_from }} as valid_from,
        {{ valid_to }} as valid_to,
        lead({{ valid_from }}) over (
            {% if partition_by %} partition by {{ partition_by }} {% endif %}
            order by {{ valid_from }}
        ) as next_valid_from
    from {{ model }}

)

select *
from ordered
where next_valid_from is not null
  and valid_to <> next_valid_from

{% endtest %}
```

Pass `partition_by` (e.g. `account_id`) once a table covers more than one
real-world entity, so gaps are only compared within the same entity's
timeline rather than across unrelated entities.

## `one_current_row`

Catches the *newest* row missing (or the previous "current" row never being
closed out) — the sibling failure mode to `no_scd_gaps`. Aggregates over
every row per entity first, then flags any entity whose current-row count
isn't exactly 1. Aggregating before filtering matters: filtering down to
current rows first would mean an entity with **zero** current rows never
produces a group to check, and the failure would pass silently.

"Current" here means `dbt_valid_to IS NULL` — that's the snapshot's own
convention for the open-ended row, not a boolean flag.

`macros/test_one_current_row.sql`
```sql
{% test one_current_row(model, valid_to, partition_by=none) %}

select
    {% if partition_by %} {{ partition_by }} as entity_id, {% endif %}
    sum(case when {{ valid_to }} is null then 1 else 0 end) as current_row_count
from {{ model }}
{% if partition_by %}
group by {{ partition_by }}
{% endif %}
having sum(case when {{ valid_to }} is null then 1 else 0 end) <> 1

{% endtest %}
```

## `valid_to_after_valid_from`

Catches an internally invalid row — `valid_to` earlier than `valid_from` on
the same row. The other two tests only check relationships *between* rows
and assume each row's own interval is already sane; this one guards that
assumption. A `NULL` `valid_to` (the current row) never satisfies `< valid_from`
in SQL, so the current row is naturally excluded without special-casing it.

`macros/test_valid_to_after_valid_from.sql`
```sql
{% test valid_to_after_valid_from(model, valid_from, valid_to) %}

select *
from {{ model }}
where {{ valid_to }} < {{ valid_from }}

{% endtest %}
```

If `dbt_utils` is already a project dependency, this one can be swapped for
the built-in generic test instead of a custom macro:

```yaml
- dbt_utils.expression_is_true:
    expression: "valid_to >= valid_from or valid_to is null"
```

## Applying them

See `snapshots/_bronze__snapshots.yml` for both snapshots wired up with all
three tests. `models/staging/_landing__sources.yml` declares the raw,
current-state-only `landing_crm` source these snapshots read from.

## Still open regardless of any of this

`unique_key` on each snapshot (`address_id`, `account_id`) has to be a value
that's stable across a rename — if the CRM source's only identifying field is
the display name itself (`Cape Twn` → `Cape Town` → `Kaapstad`), dbt snapshot
will treat each rename as a brand-new, unrelated entity rather than a new
version of the same one. That's not something any tooling choice fixes; it
depends on whether the source system actually exposes a durable ID.
